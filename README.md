# mod-tswow

This module is the AzerothCore host for TSWoW. The first working slice keeps the existing
`AddTSScripts(TSEvents*)` ABI and forwards AzerothCore world lifecycle hooks directly to
the existing TSWoW event registry.

For each subsystem, use AzerothCore core behavior and maintained AzerothCore modules first.
`mod-tswow` should provide only the adapter required to preserve TSWoW's public API or exact
event semantics. Add a generic core hook only when neither an existing AzerothCore hook nor a
maintained module exposes the required timing or mutable decision. Do not carry forward a
Trinity-era implementation when AzerothCore already supplies the feature.

Set `TSWoW.LivescriptDir` in `configs/modules/mod-tswow.conf` to the directory containing compiled
TSWoW livescript libraries. It defaults to `./lib`.
Set `TSWoW.LuaDir` there to the TypeScript-to-Lua output root when using the Lua backend. It
defaults to `./lib/lua`.

Configure from the workspace root like any other static AzerothCore module:

```text
cmake -S azerothcore-wotlk -B build/azerothcore-port \
  -DMODULES=static \
  -DTSWOW_SOURCE_DIR=/path/to/tswow \
  -DCMAKE_INSTALL_PREFIX=build/ac-port-install
```

Keep this port's build, install, configuration, data, and databases inside the `tswow-ac`
workspace. Do not install into or run from an existing `tswow-install` directory. Before
starting either server, verify that ports 3306, 3724, and 8085 are free or configure separate
database and realm ports for the port environment.

Current milestone: 352 of the 352 active inventoried events (100%), covering world, account, auction, guild,
group, vehicle, player lifecycle and combat, unit combat, creature and game-object interaction, item and
quest callbacks, packet observation, map lifecycle, spell
cast, battleground lifecycle, game events, mutable numeric events, custom client packets, mutable
battleground score serialization, player stat calculations, and livescript loading. Event groups are added as their
AzerothCore adapters are implemented, so unused legacy systems do not become dependencies. The raw inventory
contains 355 declarations; `Player.OnUpdateMeleeHitChance`, `GameObject.OnDialogStatus`, and
`Item.OnGossipHello` have no dispatch site in the pinned Trinity reference and are excluded from the active set.
Player/entity events use opaque handles and a module-owned function table, avoiding executable symbol
exports. The first player wrapper slice supports GUIDs, broadcast and addon messages, class IDs, map IDs,
teleportation, and temporary quest-reward talent points. Additional methods are added only
when a ported event or acceptance test needs them. The current player methods also cover the
gossip menu operations exercised by Test Island.
The battleground wrapper now uses public AzerothCore operations for map conversion, player enumeration,
score lookup, honor rewards, world-state updates, and ending a match. Creature respawn and corpse removal
also forward directly through the module API.

The module requires [AzerothCore's mod-ale](https://github.com/azerothcore/mod-ale), configured with
`-DLUA_VERSION=lua54`. ALE owns the Lua state, standard libraries, lock, and reload lifecycle. `mod-tswow`
adds a private TSTL environment, TSWoW bindings, callback cleanup, unit/map-scoped objects, map timers,
delayed callbacks, and outfit values to that
shared state. Keep `TSWoW.LuaDir` separate from ALE's script directory so ALE does not execute generated
TSTL files before the TSWoW bindings exist. The acceptance suite's currently used player, creature, map,
battleground, spell, and custom-packet events are bound. Plain and parameterized SQL and the generated Lua
ORM use ALE's database globals. The unchanged `tswow-tests` livescripts compile and their complete entry
point loads in the offline harness after resolving 15 test tags from a deterministic fixture. Those fixture
IDs prove replacement and loading only; a real datascript run must still supply database rows and production
IDs before server acceptance. Unresolved tags fail with an explicit error.

Custom packets use AzerothCore's existing `ServerScript::CanPacketReceive` event. TSWoW's client-to-server
opcode overlaps AzerothCore's TC9 redirect opcode, so the module consumes only packets with a valid TSWoW
fragment header and lets all other traffic continue to the AzerothCore handler. Packet assembly remains in
TSWoW's reusable `misc/client-extensions/CustomPackets` sources, which CMake compiles directly into the
module. Per-player receive buffers are module-owned and cleared on logout and livescript unload.

`Battleground.OnOpenDoors` currently forwards from AzerothCore's `OnBattlegroundStart`, which runs
later in the same start transition after doors open. Exact before/after ordering remains a parity item.

Windows validation currently covers a static AzerothCore worldserver build, an isolated seven-second server startup,
native and Lua probe loading, live unload/reload, clean shutdown, and an offline load of the complete
resolved `tswow-tests` Lua entry point, focused plain/prepared/async SQL and generated ORM checks, a fragmented
packet-runtime round trip with callback read-head reset, and an isolated full
livescript chain: TypeScript transpilation, C++ DLL compilation without core libraries, DLL loading,
`AddTSScripts` registration, custom-packet registration, typed packet reads and writes, callback cleanup,
addon-message dispatch, quest-reward talent calculation, persistent functional-event object capture, mutex and
array use, player teleportation, mutable/cancellable battleground score output, and unload. The generated smoke also covers battleground map conversion, player and
score lookup, team-aware honor rewards, world-state updates, match completion, and creature death cleanup.
An additional focused Lua probe verifies object identity, explicit `SetObject`/`HasObject`, one-shot timer
repeat counts, delayed map callbacks, the complete outfit value surface, and the player-copy-to-creature
outfit chain used by `tswow-tests`.
It also compiles mutation callbacks for resistance, armor, attack power, avoidance, hit, expertise, mana,
and rune regeneration through the public TypeScript API.

Battleground score customization uses one generic AzerothCore hook before each score is appended. The hook
can append replacement data and cancel the default score. A small public `AppendBaseToPacket` operation keeps
normal battleground and arena wire layouts inside AzerothCore. TSWoW custom score attributes remain in
module-owned storage and are removed when the battleground is destroyed.

The sixty-five added interfaces and one re-enabled existing dispatch touch ninety-nine unique AzerothCore source files. Existing-hook adapters do not modify
AzerothCore source.

An ordinary AzerothCore module can be copied into `modules/` and rebuilt unchanged. The added `PlayerHook`, `UnitHook`, `AllMapHook`, `AllSpellHook`, and
`AllBattlegroundHook` IDs are appended after AzerothCore's existing IDs, which keeps upstream numeric IDs stable. Added callbacks have default implementations,
so another module does not have to implement them. Cancellable hooks use AzerothCore's normal veto semantics and otherwise leave behavior unchanged.
Modules must be rebuilt with this AzerothCore tree because the added virtual callbacks change C++ class vtables; AzerothCore module binaries compiled against
a different core build are outside this compatibility boundary.

Any required AzerothCore source change must be generic, kept in its own commit, and wrapped at every
changed location with searchable markers:

```cpp
// @tswow-begin: short hook description
// Generic AzerothCore hook declaration, forwarding, or call site.
// @tswow-end
```

This applies to declarations, hook enums, ScriptMgr forwarding, and the runtime call site. A marker
inventory must therefore find every core change without relying on Git history.
